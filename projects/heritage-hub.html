01 / Overview

Exploring Canada's cultural places

HeritageHub is a full-stack web application designed to help people discover museums, galleries, heritage sites, and other cultural places across Canada.

The application uses cultural facility data from Statistics Canada's Open Database of Cultural and Art Facilities as its starting point. Users can browse and filter locations by category, city, province, tags, and community ratings, or explore them geographically through an interactive map.

Registered members can also contribute to the database, write reviews, upload images, and save places to a personal Bucket List or Travel Journal. Administrators have additional tools for managing facilities, users, and community content.

HeritageHub interface overview

02 / Context

From a dataset to a community experience

The project began with the idea of making Canada's cultural and heritage facilities easier to explore. The Statistics Canada dataset provided a large collection of locations, but simply presenting the data as a list would not create much of an experience for someone trying to decide where to go.

We wanted HeritageHub to combine discovery with personalization. Visitors could explore the database and map without creating an account, while registered members could save places, document visits, and contribute their own experiences.

From there, we focused the application around three main things: discovering places, learning more about them, and keeping track of places users had visited or wanted to visit.

03 / Planning

Defining the application structure

Before development, we mapped out the main user roles and the different experiences each type of user would have. Visitors could browse facilities and use the map, members could interact with the content and maintain their own lists, and administrators could manage user-generated content.

We also planned how the frontend, backend, and database would communicate. The React frontend would request data from a Node.js and Express backend, while MongoDB would store facilities, users, reviews, and personalized user information.

This also meant the backend needed to distinguish between public requests, authenticated member actions, and administrator actions. Planning these permissions early gave us a clearer structure for implementing protected routes and authorization later in development.

04 / Database

Structuring the data

MongoDB was used to store the application's facility, user, and review data. We created Mongoose schemas to define the structure of these collections and how different pieces of information related to one another.

Facility documents store information such as the facility name, category, address, province, city, coordinates, tags, and user ownership. User documents contain account information, roles, and the facilities associated with their Bucket List and Travel Journal.

Reviews were structured around a specific facility and user, with each review storing a rating, comment, timestamp, and optional image. This made it possible to retrieve reviews for individual facilities and calculate their average ratings.

05 / Backend

Building the API

I set up the Express server and established the connection to MongoDB Atlas, then developed the Mongoose schemas and core API routes for authentication, facilities, and reviews.

I developed endpoints for registering and authenticating users, retrieving and managing facilities, creating and deleting reviews, and managing user-specific Bucket List and Travel Journal data.

I also created the seed script used to populate the database from the provided CSV dataset. This gave us a repeatable way to import the facility data into MongoDB rather than manually entering each location.

06 / Authentication

Handling accounts and permissions

HeritageHub uses JSON Web Tokens for authentication. When a user logs in, the backend authenticates their credentials and returns a JWT that is used to authorize protected requests.

I implemented the authentication flow and the verifyToken middleware used to protect routes that require a logged-in user. Passwords are hashed before being stored in the database using bcrypt rather than being saved as plain text.

The application also distinguishes between member and administrator permissions. Members can manage their own contributions, while administrators can manage content and users across the application.

07 / Features

Connecting features to the user experience

I developed the functioning features for the Travel Journal, Bucket List, Add Review, and Facility Details pages. These features connect the user's actions in the React interface to the backend and database.

On facility pages, users can view location information, ratings, reviews, and uploaded images. Members can add their own review, upload an image, mark a location as visited, or save it to their Bucket List.

I also implemented review averaging and review image displays on facility cards, along with pagination and filtering functionality for the home page. These features helped make the large facility dataset easier to browse.

08 / Challenges

Working through unexpected problems

One of the more difficult parts of development was getting image uploads to work correctly. Our first implementation successfully uploaded images to MongoDB, but the stored data was not in a format that the application could display. After researching the issue, I changed the implementation to convert uploaded images into Base64 strings, which allowed them to be stored and displayed correctly.

We also encountered an issue with deleting facilities. If a facility was deleted while it was still saved in a user's Bucket List or Travel Journal, the application could crash because the user's stored reference no longer pointed to an existing facility.

I fixed this by updating the facility delete route to use User.updateMany and remove the deleted facility from users' Bucket Lists and Travel Journals. This allowed the related user data to stay consistent after a facility was removed.

09 / Outcome

A working full-stack application

Final HeritageHub screenshots

The final HeritageHub application brings together a searchable cultural facility database, interactive map, authentication system, reviews, image uploads, and personalized travel features.

Visitors can browse and explore facilities without an account, while members can create contributions and maintain their own Bucket List and Travel Journal. Administrators have additional controls for managing facilities, reviews, images, and users.

The project demonstrated that the original dataset could support much more than a searchable directory. By combining it with user accounts, reviews, images, saved locations, and an interactive map, we turned the data into an application people could actually use to plan and document their experiences.

11 / Reflection

What I learned

HeritageHub gave me a much stronger understanding of full-stack development. I became more comfortable working with React on the frontend and Node.js, Express, and MongoDB on the backend, particularly with how data moves between each part of an application.

Working with MongoDB also taught me how much database structure can affect the rest of an application. Designing the User, Facility, and Review schemas made me think more carefully about how information should be organized, connected, and retrieved.

I also gained a better understanding of authentication and security through implementing JWTs and the verifyToken middleware. Building features such as the Bucket List, Travel Journal, and reviews showed me that the backend needs to account for different user permissions and possible edge cases, not just the expected user flow.

At the same time, the project strengthened my understanding of user interface and interaction design. While developing features, we constantly had to consider how someone would navigate the application, what information they would need, and what could make an interaction confusing or frustrating.

One of my biggest takeaways was becoming more confident in connecting technical decisions with the overall user experience. HeritageHub showed me that the interface and the systems behind it have to work together for an application to feel reliable and easy to use. If we continued developing the project, I would be interested in improving features such as map marker clustering, password resetting, and the facility tagging system.
